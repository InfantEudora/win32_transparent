Goal (agreed 2026-09-04): give reactphysics3d a proper vehicle/wheel-suspension constraint modelled on Jolt's `Jolt/Physics/Vehicle/` (checkout at `C:/code/JoltPhysics`), then replace the hand-rolled raycast suspension in the game. Library work in `C:/code/reactphysics3d`, branch `vehicle-constraint` (off `crane_testbed`), one small commit per step. Library steps 1-8 DONE 2026-09-04 (AxisConstraintPart/SpringSettings, allocator fix, SpringJoint, VehicleConstraint incl. hard stop/friction/steer/drive/brake, UprightConstraint + spin damping, implicit gyroscopic integration, testbed scenes Spring 18 / Vehicle 19 / Upright 20). Later library commits: 17663e66 multi-sample wheel rays (`numContactSamples`, origin offset radius*sin(angle) along the rolling direction, rays stay parallel), cbead97a `VehicleWheelSettings::enabled`, be94edfe `warmStartImpulseRatio` (0.8, Jolt's) on the lateral/hard-stop parts - without it equal-and-opposite lateral impulses on one axle persist for ever and eat the tires' grip (buggy snapped round after corners). Anti-roll bar NOT done (deferred). ShipCharacter stays on its existing stabilisation by the user's decision (2026-09-05: "already keeps it super stable, small enough to let it sit") - do not propose moving it onto UprightConstraint again unless asked.

GAME INTEGRATION DONE 2026-09-05 (game repo commits after b4d0b70): `core/Vehicle` owns an `rp3d::VehicleConstraint` (`CreateVehicleConstraint` from `wheels`, `SyncWheelSettings` each tick so debug-UI drags apply, `ReadBackWheels` into the Wheel diagnostics, `UpdateWheelVisuals`); `WheelSuspension::UpdateContact` is gone, TankCharacter/BuggyCharacter only set drive/brake torque and steer per wheel. Mapping: stiffness/damping in STIFFNESS_AND_DAMPING mode (same numbers -> same ride height, 11.1 vs 11.2 mm), `friction_coefficient` -> longitudinalFriction, `lateral_friction` is now a Coulomb mu (tank 0.5, buggy 1.0; was a viscous N/(m/s) rate), `can_contact_ground` -> enabled, game wheel angular_velocity = -rp3d (negative when rolling forward). The tank's idle brake must not be applied while driving (brake torque wins in rp3d). `Vehicle::GovernedDriveForce` is a rev limiter (torque clamped to I*dw/dt to reach top_speed) - a plain on/off cap at top_speed saw-tooths because one tick of torque on a 5 g m^2 wheel adds ~90 rad/s. Body linear damping 0.5 (set by Physics::AddBoxCollider) makes the suspension carry 99% of the weight - expected, not a bug.

Verification tooling (game repo): `tools/vehicle_mcp.py` drives `wind.exe` over stdio JSON-RPC (port 8765 is often held by another project's wind.exe - check `Get-Process wind | select Path` before assuming the Tank app is running), `baseline --vehicle tank|buggy --out f.json` runs settle/drive/coast/brake/turn deterministically via tank_pause/tank_reset/tank_step; `compare a b`. `tools/baseline_handrolled_*.json` (pre-migration, recorded from a `git worktree` of b4d0b70 with `--exe`) vs `tools/baseline_rp3d_*.json`. MCP tools take `vehicle` arg. The scene has a crane rig at (3.5,0,2), a speed bump at (0,0,4), obstacles and a 20 m ground plane with heightmap terrain beyond -z: scripted drives must stay short (buggy turns left).

Threading gotchas found: anything touching the body from the MCP/render thread races the physics step - `Vehicle::RequestReset` queues resets for the physics thread; `Scene::UpdatePhysics` decrements `pending_physics_steps` AFTER the tick (tank_step used to return mid-step). `Vehicle::ReleaseInputs` used to leave gas_pedal set (Brake(0) only) - fixed.

**Why:** rp3d had no springs/soft constraints; the game's explicit spring/damper had a c*dt/m stability cliff, weak viscous lateral grip (tank pivoted at 8.9 rad/s, now 1.4), a brake that couldn't stop the tank and a buggy that flipped under braking.

Game: `mingw32-make -j8 APP=Tank` with `/c/msys64/mingw64/bin:/c/msys64/usr/bin` on PATH.
