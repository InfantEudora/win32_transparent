**Direction agreed with the user 2026-09-06.** The engine should become a deterministic lockstep simulation, the way multiplayer games are built: randomness comes from a seed, physics advances in fixed ticks, and **the only thing that mutates the simulation is input, stamped with the tick it applies to**. A session is then reproducible from a small recorded input stream — an hour of gameplay replays to the identical end state. Frame rate becomes irrelevant, and there need not be frames at all (headless runs are possible; nothing on the physics thread needs the GL context, only `Init()` currently does).

**The reframe that matters: `MCPServer` is just another "player", and so is the UI.** Neither may touch simulation state directly; both submit input through `InputController` like a keyboard does. This replaces — rather than patches — the four problems in [[threading-model]]: the MCP race, the frame-rate-vs-tick-rate mutation mismatch, the ad-hoc `Vehicle::RequestReset` / `pending_physics_steps` deferrals, and the wall-clock latches.

**Input must be a serialisable value type, not a closure.** An earlier suggestion of a `std::function` command queue was explicitly rejected for this reason: closures fix the races but cannot be recorded or replayed. POD events can.

**Migration path that avoids rewriting ten apps:** `InputController` today is a *polled state* design (`IsKeyDown`/`WasKeyReleased`/`GetDelta` over `KeyState`), but lockstep needs an *event stream*. Keep both: make the tick-stamped event stream the boundary, and **derive** the polled `KeyState` from that tick's events at the top of each tick. All existing gameplay code keeps calling `IsKeyDown(INPUT_MOVE_LEFT)` unchanged, while replay just feeds a recorded stream the sim cannot distinguish from a live one.

**Sim input vs view input must not mix**, or every camera pan perturbs a replay. Camera control, hover, selection and ImGui panel state are view-local and must never enter the stream — note `InputController` currently holds both kinds (`hovered_object`/`hovered_normal`/`hovered_position` alongside the movement keys). Sharp edge: **object picking depends on the rendered frame** (the ID-buffer readback in `CheckObjectSelection`), so "click at (x,y)" is not replayable — the resolved *object id* is the input. That is also what real multiplayer games do: the client resolves the pick locally and ships the entity id.

**Deliberate scope limit (user, 2026-09-06):** same-binary, same-machine replay is the goal and is where the value is (deterministic MCP experiments — run, change something, compare). Cross-machine/cross-architecture float agreement is explicitly NOT a goal: *"We are FAR away from our floating points behaving the same on a different architecture."* Don't propose fixed-point or strict-FP work. Design so it isn't precluded, don't pay for it.

**Blockers found, with the user's rulings:**
1. **Variable timestep.** `UpdatePhysics(1.0f / physics_tps * physics_time_factor)` scaled `dt` by the global time factor (6 call sites + a "Global Time Factor" UI slider). Ruling: **the timestep is just 50 Hz, no scaling.** Also `TankCharacter`/`BuggyCharacter::UpdatePhysicsState` each hardcode `float timestep = 0.02f`.
2. **`Vehicle` hold-latches on `GetTickCount64()`** (~15.6 ms granularity against a 20 ms tick, and real time rather than sim time, so holds break under pause/`tank_step`). `ApplyHoldLatches()` is called exactly once per tick per vehicle from each subclass's `UpdatePhysicsState`, so a plain tick countdown works.
3. **Unseeded `rand()` in sim logic** (`ApplicationDozer.cpp:214`, `core/type_helpers.cpp:125`; `ApplicationTank.cpp:1331` does `srand(1337)` but that seeds the *global* C RNG shared with any other caller). Ruling: **it should all go through `RRandom`.** Not yet done.
4. **Animation timing is sim state** since the root-motion rewrite (extracted deltas drive the capsule), so `Object::animation_time_delta` (default hardcoded `0.02f`) must be tick-derived. Ruling: *"Animation time delta there means 20ms. But should be set from 1/physics_rate."*

**Ordered plan (agreed):**
1. **DONE 2026-09-06.** Promote the physics-thread-local `physics_ticks` counter to an authoritative atomic tick on `Scene`. Everything else hangs off it. It must advance only when a tick actually runs (not while paused), so it counts sim time, not wall time.
2. **DONE 2026-09-06.** Make `dt` constant; `physics_time_factor` scales the tick *rate* (pacing), never the timestep.
3. **DONE 2026-09-06** (both commits, see below). `InputEvent` POD + tick-stamped queue, `KeyState` derived from it, a real lock, then Raw Input on its own thread with real edges and the gamepad folded in.
4. **DONE 2026-09-06.** Convert `Vehicle` latches to tick countdowns; keep ms at the MCP boundary (the MCP/network layer speaks milliseconds, the sim speaks ticks).
5. **DONE** - input side 2026-09-06, command side 2026-09-07 (the SimCommand queue, below). Route MCP through it as a player — `RequestReset` is deleted. (The `pending_physics_steps` decrement-ordering hack is still there.)
6. **DONE 2026-09-10** (except the animation controls - see below). Route the UI through it.
7. Record/replay harness + state hash. **Keystone: until you can replay and compare, you cannot know whether any of the above achieved determinism.** `tools/vehicle_mcp.py`'s baseline-JSON compare is this in embryo.

Step 7 is all that remains, and it is the keystone.

**What landed on 2026-09-06 (steps 1, 2, 4 + blocker 4):**
- `Scene::GetPhysicsTick()` — `std::atomic<uint64_t>`, incremented at the very END of a tick that actually ran, for the same reason `pending_physics_steps` is decremented there. Two dead counters (a `Scene::physics_ticks` member and a `PhysicsThreadFunction` local feeding a commented-out log) were consolidated into it.
- `Application::GetPhysicsTimestep()` — `1.0f / physics_tps`, constant, now the single source for all 7 `UpdatePhysics`/`UpdateAnimations` call sites across the apps. `physics_time_factor` moved to the pacing line in `PhysicsThreadFunction` (`us_looptime_desired = physics_us_per_tick / max(factor,0.01f)`, recomputed per loop) and its UI slider is relabelled "Time Factor (tick rate)".
- `Scene::GetPhysicsTimestep()` + `Object::physics_timestep`, pushed to each object before `UpdatePhysicsState()`. This retired the hardcoded `float timestep = 0.02f` in `TankCharacter`/`BuggyCharacter::UpdatePhysicsState` without touching the 13-class `UpdatePhysicsState()` virtual signature.
- `Object::animation_time_delta` is refreshed from the sim timestep every tick by `Scene::UpdateAnimations(float)`, with `f_animation_time_delta_override` (set by the debug slider, cleared by a "Follow tick rate" button) so the drag isn't overwritten. Note the pre-existing, differently-purposed `f_animation_override` next to it.
- `Vehicle` latches are `gas/brake/steer_latch_ticks` countdowns decremented in `ApplyHoldLatches` (called exactly once per tick per vehicle). `GetTickCount64` is gone from `Vehicle`. `ApplicationTank::DurationMsToTicks` / `TicksToRealMs` convert at the MCP boundary (rounding up, so a sub-tick duration still gives one tick).

**Step 3, commit 1 of 2 — landed 2026-09-06 (input event stream + lock, acquisition unchanged):**
- `InputEvent` POD in `core/InputController.h` (`type`, `mapped_keycode`, `value`) with `INPUT_EVENT_KEY_DOWN/UP`, `AXIS_ABSOLUTE` (value IS the new value — polled mouse position), `AXIS_RELATIVE` (value is added — wheel, and raw mouse delta later).
- `SubmitEvent()` (any thread) / `ApplyPendingEvents()` (physics thread, drains into `KeyState`) / `GetTickEvents()` (what this tick actually ran with — the hook a recorder and a replayer both attach to) / `PollDevices()`. `UpdateKeyState()` is now just `PollDevices()` + `ApplyPendingEvents()`, so its single call site in `Scene::UpdateInput` is unchanged.
- **`PollDevices` deliberately re-states each key's LEVEL every tick rather than emitting edges.** That is what made this commit provably behaviour-preserving, quirks included: `Down()` is idempotent while `Up()` only decrements, so a keycode with two mappings (LSHIFT/RSHIFT → `INPUT_SHIFT`) still reads down for one extra tick after release. Commit 2 turns levels into real edges and fixes that counting bug **on purpose**.
- One `std::mutex state_mutex` guards only the cross-thread handoff — the pending queue plus a new `WindowInputState` struct collecting the fields the window/render threads write (`window_position`, `f_mouse_over_window`, `hovered_normal`, `hovered_position`). `KeyState` is NOT in it, so the hot lock-free `IsKeyDown`/`GetDelta` path gameplay hits many times a tick is unchanged. This retired the `hovered_normal` "How to atomicise this?" TODO.
- The wheel no longer writes `KeyState` straight from the window thread while the physics thread reads and clears it — it submits an `AXIS_RELATIVE` event.
- **`Application::UpdateInput()` moved INSIDE `physics_mutex`** (it writes `KeyState`, which the render thread reads under that same mutex from `DrawImGuiUI`). `NextInput()` deliberately stayed *after* the sleep — the render thread consumes mouse deltas via `UpdateUICameraControls`→`GetDelta` in that window, and clearing edges at end-of-tick would break camera mouse-look — but is now wrapped in its own brief lock. Lock order is always `physics_mutex` → `state_mutex`, never the reverse.
- **Focus gating** (user asked for it: the sim used to respond while alt-tabbed, via `GetAsyncKeyState`'s global reads). `f_has_focus` is maintained from `WM_ACTIVATE`/`WM_SETFOCUS`/`WM_KILLFOCUS` in `HandleMessage` — which works because `Window`'s WndProc forwards **every** message to it unconditionally after its own switch. Unfocused, keys are reported as UP rather than not sampled, so nothing stays latched. The cursor position keeps tracking regardless (it is view data for picking/UI, not sim input). ImGui is unaffected — `imgui_impl_win32` has its own handler. Caveats: `f_has_focus` defaults to **true**, so if a window never receives an activation message the old global-poll behaviour persists (safe fallback, but the gate may not engage for a process spawned unfocused); and if an app ever runs more than one window sharing one `InputController` (the readme's `num_threads` multi-window mode), focus transfer between them would toggle the flag.
- Runtime-unverified: the focus gate itself was confirmed by code inspection, not by an alt-tab test.

**Step 3, commit 2 of 2 — landed 2026-09-06 (Raw Input on its own thread, real edges, gamepad merged):**
- New `core/RawInput.h/.cpp`: `RawInputSource` spawns a thread that creates a **message-only window** (`HWND_MESSAGE`) and pumps it. A window's messages belong to the queue of the thread that CREATED it, which is what makes this immune to the title-bar-drag stall (`DefWindowProc` runs a nested modal loop for the duration of a drag/resize — the same reason render and physics already have their own threads).
- Registered `RIDEV_INPUTSINK`, which is **required** when naming an explicit `hwndTarget` and delivers regardless of foreground — necessary because a message-only window can never BE the foreground window, so a foreground-mode registration pointed at it would deliver nothing. Focus filtering is therefore done in `InputController` (which already had it).
- **Never `RIDEV_NOLEGACY`**: ImGui's Win32 backend needs the ordinary `WM_KEYDOWN`/`WM_CHAR`/`WM_MOUSE*` on the main window. Raw Input runs *alongside* the normal message flow, so `SetRawInputActive(true)` tells `InputController` to stop polling keys and to ignore `WM_MOUSEWHEEL` (`RI_MOUSE_WHEEL` already reported it — otherwise every notch doubles). If `Start()` fails it is never set and the polling path stays in charge; the fallback also emits edges now, by diffing `GetAsyncKeyState` against each mapping's `f_held`.
- Raw keyboard reports the **sideless** modifier VKs, but the keymap is built from sided ones (`VK_LSHIFT`/`VK_RSHIFT` both → `INPUT_SHIFT`), so `VK_SHIFT` is resolved via `MapVirtualKey(MakeCode,MAPVK_VSC_TO_VK_EX)` and CONTROL/MENU via the `RI_KEY_E0` flag — without that, none of them would ever match a mapping. `VKey == 0xFF` filler events are dropped.
- **Real edges, and the multi-mapping bug fixed on purpose:** `KeyState::f_isdown` is now a count of currently-held *mappings*, maintained per `KeyMap::f_held`; `f_was_released` fires when the last one comes up. `KeyState::Down()`/`Up()` are gone. A key event carries its system keycode in `InputEvent::value` so the applier resolves the exact mapping (`value == 0` means synthetic, i.e. what the UI/MCP will submit in steps 5-6).
- New `INPUT_MOUSE_DELTA_X/Y` fed by raw movement: unaccelerated, unclipped, device-resolution. **Existing camera code still reads the `INPUT_MOUSE_X/Y` cursor delta** — switching it over is one line per call site but changes feel/sensitivity, so it was deliberately left as the user's call.
- `f_release_all_keys` on focus loss releases everything held on the next tick, so nothing can stay latched across an alt-tab.
- **`GamePadController` is deleted**, absorbed into `InputController` with the same API names (`ListDevices`/`AddGamePadMap`/`GetNormalizedAnalogValue`/`SendMotorData`/`lmotor`/`rmotor`) and identical analog indices, normalisation and rumble decay, so `ApplicationShip` and `ApplicationTank` migrated by pointing their `gamepad_controller` member at `main_window->inputcontroller` and deleting their per-app `UpdateKeyState()` poll. Improvements: all four XInput slots instead of hardcoded 0, reconnect via a `GAMEPAD_RESCAN_TICKS` (50 ≈ 1s) countdown **because `XInputGetState` on an EMPTY slot is expensive and XInput has no hotplug notification**, analog values zeroed on disconnect (the old code left a yanked stick at its last deflection and never looked again), and focus-gated like the keyboard. `SendMotorData` uses `dev_index` rather than slot 0. Note the apps' `GAMEPAD_*` keycodes are still app-local `#define`s at `INPUT_LAST+n`.

**Verified:** all 10 apps build except `Grid`, which was ALREADY broken at HEAD by the animation rework (`PlayerCharacter::SetNextAnimation` no longer exists) — unrelated and untouched. `ApplicationUI` and `ApplicationGrid` had long-stale no-arg `main_scene->UpdatePhysics()` calls that could never have compiled; both fixed in passing, so `UI` builds again. `tools/vehicle_mcp.py` baselines for BOTH tank and buggy come back **bit-identical** to `tools/baseline_rp3d_*.json` (82 fields, 0 differing; `coast_distance` matching to 17 significant figures) — the refactor is behaviour-preserving. Re-run after step 3 commit 1 AND commit 2: still 0 differing for both vehicles. Raw input confirmed live at runtime (registered, thread running, "Raw input active"), and the merged XInput path enumerated a real controller ("X-Input: Controller at 0"). NOT verified: actual key/mouse/pad INPUT behaviour - the baselines are MCP-driven and press nothing, so edges, raw deltas, the focus gate and the gamepad still want a hands-on test.

**Already in the codebase's favour:** the tick is already fixed at 50 Hz and not frame-coupled; rp3d 0.10 is single-threaded and is a fork the user controls ([[rp3d-local-fork-hinge-motor-patch]]); `Object::GenerateUniqueID()` is a plain `object_ids++` counter (deterministic given deterministic creation order, no addresses or hashing); `RRandom` is already designed around a seed index into a noise texture.

Related: [[threading-model]], [[project-overview]], [[rp3d-vehicle-constraint-plan]].

**Step 5 — MCP as a player (2026-09-06):**
- `InputController::HoldKey(keycode,ticks)` / `HoldAxis(keycode,value,ticks)` / `ReleaseSynthetic()` / `GetAxis()`. A hold emits an **ordinary** `KEY_DOWN`/`AXIS_SCALAR` now and an ordinary release when it runs out, so a recording cannot tell scripted input from a human — the hold is a convenience for the CALLER, never a concept the sim knows about. New `INPUT_EVENT_AXIS_SCALAR` + `InputEvent::fvalue` carry non-binary controls (user: *"Each input that isn't a binary action will take a scalar like this"*).
- **`Vehicle::HoldDrive`/`HoldBrake`/`HoldSteer`/`ApplyHoldLatches` and the `*_latch_ticks` members are DELETED.** They only ever existed because an MCP round trip can't out-pace the tick rate, which is the same problem a synthetic key press has - solved once, generically, instead of once per subsystem.
- `ApplicationTank` defines scalar axes `INPUT_AXIS_DRIVE/STEER/BRAKE` (`INPUT_LAST+20..22`, registered with `AddKeyMap(0,...)`), applied in `RunSimulationTick` alongside the keyboard and gamepad. `tank_drive`/`tank_steer` call `SetControlledVehicle(vehicle)` then `HoldAxis` - "which vehicle" now means "take control of it", because a player drives what it controls.
- **Trap found and fixed: hold countdowns must advance on SIMULATED ticks.** `Application::UpdateInput()` runs on every physics-thread loop *including while paused*, so a naive per-call countdown put hold durations back on wall-clock time - the exact bug tick-denominating them was meant to remove. `ApplyPendingEvents(sim_tick)` now takes `Scene::GetPhysicsTick()` and advances holds only when the clock actually moves.
- **Hardware vs scripted focus gating.** `ApplicationTank`'s tick hook's blanket `if (!f_has_focus) return;` is gone (it would have silenced MCP exactly when the window isn't in front, i.e. every automated run). Keyboard/gamepad/fire are wrapped in `if (has_focus)`; scripted input is deliberately ungated because it doesn't come from the OS.
- **Latent bug found and fixed in `TankCharacter`: `idle_brake` is now a FLOOR** (`max(brake_pedal,idle_brake)`). The gamepad path writes pedals unconditionally, so `Brake(gp_r2)` with a connected-but-idle controller was `Brake(0)` and wiped the "permanent rolling resistance" entirely - the tank coasted 1.2m instead of 0.16m. Reachable at any time by plugging in a pad and clicking the window; it stayed hidden only because scripted runs happened not to have focus. `tank_telemetry` now reports `window_focus` so a baseline diff can tell focus-dependent behaviour from a physics change. **Note the two vehicles have different pedal-lifetime models**: `TankCharacter` self-clears (`gas_pedal=0; brake_pedal=idle_brake`) at the end of its tick, `BuggyCharacter` does NOT and relies on the tick hook writing every tick - which is why the gamepad's `Accelerate(0)` can't simply be dropped.
- **Baselines no longer match exactly, and that is expected.** settle/drive/coast/brake match to <1e-4 for both vehicles. Tank coast position differs by 0.016m; the buggy's `turning`/`after_turn_rest` differ (0.11m position, 0.17 m/s). Cause: MCP input now goes through the app's tick hook like a keyboard, one tick earlier than the old `ApplyHoldLatches` back door, and steering is *incremental* (`steering_position += 0.10*factor` per call) so a one-tick shift changes the deflection reached. `tools/baseline_rp3d_*.json` were recorded against a back door that has deliberately been deleted, so they want **re-recording** rather than the code being contorted to reproduce them. NOT yet re-recorded - the user's call.

**Step 5, command side — the `SimCommand` queue (2026-09-07).** Input covers "a player pressed something"; it cannot express "create this object here". Those — the debug UI's create/modify and the MCP *command* tools — go through a second, parallel stream. Design agreed with the user before building:

- **The command is DATA, the handler is CODE.** `core/SimCommand.h` is a fixed-size, trivially-copyable POD (a `static_assert` enforces that, so nobody can put a `std::string` in it); the code that acts on one is a `std::function` registered against a type number on the `Scene`. A virtual `Command::Apply()` hierarchy was rejected for the same reason the `std::function` *queue* was rejected for input: a vtable pointer is not data, so such a queue can be executed but never recorded. Only the struct is ever written to a replay log, so the handler being a closure costs nothing.
- **That split is what makes it extensible.** Core owns types below `SIM_CMD_LAST`; an app numbers its own from `SIM_CMD_LAST+n` (the same convention the input keycodes use with `INPUT_LAST`) and registers a handler closing over its own classes. `ApplicationTank`'s `TANK_CMD_VEHICLE_RESET` closes over `controlled_tank`/`controlled_buggy` — types core has never heard of — while core still carries, orders, counts and (later) records the command like any other. This was the user's explicit requirement: *"any app should be able to extend on it with only the extended classes it knows about."*
- **`version` is the FIRST field** (user's call), so a reader validates it before trusting any other offset. Bump it on any layout change *and* on any change of meaning — a field that keeps its type but starts meaning something else is exactly the case a reader cannot otherwise detect. This is the accepted price of a fixed payload.
- **Objects are addressed by `objectid_t`, assets by a new `assetid_t`** — never by pointer (not replayable, and possibly freed by the time the physics thread gets there).
- **API:** `Scene::SubmitCommand` (any thread, returns a sequence number) / `GetAppliedCommandSequence` / `GetCommandResult(sequence)` / `RegisterCommandHandler` / `GetPendingCommands`, plus `Application::SubmitCommandAndWait` for the common MCP case.
- **Drained at the top of `UpdatePhysics`, BEFORE the pause early-return.** A paused sim is exactly when the UI and a scripted session do most of their creating and teleporting; if commands only ran on a stepping tick, a paused editor would freeze and every waiting caller would time out. Verified: a teleport applies while paused.
- **A handler returns the object it created or acted on**, and the result is stored in a 64-entry ring keyed by sequence. This is the only way a spawn can report WHAT it spawned: ids are handed out on the physics thread in tick order, which is precisely what makes them reproducible, so the submitter cannot know the id in advance.
- **Sharp edge: the debug UI must submit and NOT wait.** `DrawImGuiUI` runs with `physics_mutex` held, so waiting there for the physics thread — which needs that same mutex to reach `DrainCommands` — deadlocks instantly. Documented on `SubmitCommandAndWait`; the UI's two reset buttons submit and see the result next frame. MCP threads hold no locks and may wait.

**`assetid_t` — a hash, deliberately not an index (2026-09-07).** `AssetManager` had no id at all. The obvious choices (a vector index, or a counter handed out at load time) are stable only until someone inserts or reorders an `AddNewAsset` call in `Init()` — after which an old recording binds to the WRONG asset, silently, and the `version` field cannot catch it because the struct did not change. So `assetid_t` is **FNV-1a over the asset's name, derived and never assigned**: effectively "the name in 4 bytes", independent of load order, and a renamed or removed asset simply fails to resolve instead of hitting something else. `Asset::SetName()` is the only way the name is set (there are two `new Asset()` sites — `AddNewAsset` and `AddNewAssetFromOBJFile`, the latter not routing through the former — which is why it is a function and not two assignments), `RegisterAsset` warns on an id collision at load time, and `GetAssetByID`/`GetObjectFromAssetID` are linear scans like `GetAsset` (tens of assets, called on spawn, not per tick). Verified identical ids across separate runs.

**What moved over, and two new tools.** `object_set_transform` and `tank_reset` now submit commands (`tank_reset` also *waits*, so it returns the POST-reset state — it used to return the pre-reset state and leave the caller guessing when it had landed). `Vehicle::RequestReset`/`ApplyPendingReset` and their calls in both subclasses' `UpdatePhysicsState` are **DELETED** — that was a private, one-off deferral queue for exactly one operation. `asset_list` and `object_spawn` were added because `SIM_CMD_OBJECT_SPAWN_ASSET` would otherwise be untested code; both verified at runtime (spawn by name and by id, while running and while paused, distinct sequential ids, both error paths). There is deliberately **no `OBJECT_DESTROY`**: nothing in the engine removes an object from a scene yet, so there is no teardown path to call.

**Verified 2026-09-07 by A/B against HEAD** (stash only the change set, build, record, pop, rebuild — the clean way to attribute a diff when the working tree also holds the user's own edits):
- **Tank: identical.** Max absolute difference across 669 numeric fields is 5e-6, on wheel angular velocities that are themselves ~1e-6.
- **Buggy: identical through settle/driving/coast/braked**; the `turning` trajectory shifts by 0.075 m and `after_turn_rest` by 0.113 m. Cause: the reset now lands BEFORE the tick's physics step instead of after it. Under the old code the first stepped tick ran with the *pre-reset* pose **and** the new drive/steer input, then got reset at the end of `UpdatePhysicsState`. Removing one settle tick closes only about half the gap, confirming it is the ordering and not merely a spare tick. The new ordering is the correct one; the baselines want re-recording (already the case, see step 5's note above).

**Also confirmed 2026-09-07: the tank's scripted baseline is all zeros at HEAD, and it is not a regression.** `TankCharacter::direct_track_control` now defaults to **true** (committed in 6cadccd as an in-game test rig), and that path ignores `throttle_input`/`steer_input` — which is exactly what MCP `tank_drive`/`tank_steer` feed. **Finding worth chasing before step 7: the scripted coast phase is intermittently non-deterministic AT HEAD.** Two runs of the *same* HEAD binary gave `coast_distance` 0.561 vs 1.288, with buggy wheel angular velocities of +1.28 vs -8.21 rad/s — while every other phase matched. Three consecutive runs of the post-change build all gave 1.2879 exactly, and HEAD's second run gave the identical 1.2878966, so the stable value is reproducible and the 0.561 was the outlier. The whole scenario runs paused and advances via `tank_step`, so this is NOT machine-speed jitter in the pacing; the likely culprit is that an input event submitted from the MCP thread lands on whichever tick the physics thread reaches next, so the `tank_drive direction=stop` before the coast can be released one tick late. **That is exactly what step 7 has to fix**: an input event should carry the tick it belongs to, chosen by the submitter, the way a command carries its sequence. Not yet confirmed — reproducing it reliably needs a few dozen runs.

**Step 6 — the debug UI on the queue, and the panel restructured (2026-09-10).** Done, with animation deliberately left out (the user's call).

*What was on the panel, and where it went.* Everything that changes simulation state now submits a `SimCommand`: the transform controls, all ten object physics properties, world gravity, Duplicate, Destroy, the collider-gizmo button, and the menu bar's Add > Empty/Camera/Light/Asset. Everything that only changes what is DRAWN stays a direct call, deliberately — renderer flags, VSync/MSAA/alpha clip, materials, `material_slot[]`, light colour/brightness/shadow bias, the camera, and `SetVisibility` (which only touches `f_visible`). Putting view state in the stream would perturb a replay for no gain. Pause / step / time factor / TPS also stay direct: they change how OFTEN a tick runs in real time, never what a tick computes.

*The UI was never racy* — `DrawImGuiUI` runs with `physics_mutex` held, so it is already mutually exclusive with the whole tick. This step was about determinism, not safety, which is why it could be done as a straight substitution.

**The deadlock that shapes the UI's whole relationship to the queue.** UI code must submit and NEVER wait. `DrawImGuiUI` holds `physics_mutex`; the physics thread needs that same mutex to reach `DrainCommands`; so `SubmitCommandAndWait` from the render thread deadlocks on the spot. Hence `Application::SubmitUICommand` — fire and forget, and the panel shows the new value on a later frame, which is how an ImGui widget behaves anyway since it re-reads the object every frame. The visible consequence: the Duplicate button cannot select the copy it just made, because the copy's id only exists once the physics thread has applied the command.

**SIM_COMMAND_VERSION is now 2.** Grew `subtype`, `velocity`, `angular_velocity`, `bool_values`, `collision_category_bits`, `collide_with_bits`. Two design points worth keeping:
- Reusing `position` to mean "velocity" in one command and "position" in another was considered and rejected: a fixed payload rots the moment one field means two things. Separate named fields, and the struct is ~120 bytes, which is irrelevant next to that.
- A boolean property is a PAIR of bits — the `SIM_CMD_FLAG_*` says "I am setting this one", the bit at the SAME position in `bool_values` says what to. That alignment is what keeps each one to `if (flags & F) Set(bool_values & F)` instead of a parallel table.
- One `SIM_CMD_OBJECT_SET_PHYSICS` covering all nine properties, rather than nine command types, because they share SET_TRANSFORM's shape: "here is a set of properties, the flags say which I mean".

**New MCP tool `sim_command`** submits a raw command by name (`object_set_physics`, `object_spawn_primitive`, …) or by raw number for an app type. It exists for two reasons: the handlers are otherwise only reachable by clicking a button, so they would ship unexercised, and a record/replay harness needs exactly this — a recording IS a stream of these. Note `applied` only means the queue drained it; a handler that found no such object still counts as applied, so the tool adds a `note` when a command acted on nothing.

**The panel is now three docked windows.** Docking was never actually enabled — the submodule sits on imgui's `docking` branch but `ImGuiConfigFlags_DockingEnable` was absent from `Window::InitImGui`. With it set, `RenderApplicationUI` (still the single call each app's `DrawImGuiUI` makes) hosts a `DockSpaceOverViewport` with `ImGuiDockNodeFlags_PassthruCentralNode` — the passthru matters, or the host window paints over the viewport and swallows every click that `CheckObjectSelection` needs. A default layout is built once via `DockBuilder`, and only when `DockBuilderGetNode` returns NULL, so a layout the user arranged by hand is not thrown away each start. Scene and Engine share the upper-left node as tabs, Inspector takes the lower-left, viewport keeps the centre.

*The density fix that mattered* was the Inspector becoming a TAB BAR (Transform / Physics / Render / Animation / Debug) rather than fifteen stacked collapsing headers, and a tab not being submitted at all when the object lacks that aspect — replacing the three disabled `No Mesh`/`No Physics`/`No Skeleton` headers that used to spend three lines each saying what an object ISN'T. Read-only internals (bone matrices, skeleton bone lists, mesh counts) moved behind the Debug tab so they stop competing with controls. The tree got selection highlighting, which it never had, and a name filter that switches it to a flat list of matches (the tank scene is 59 objects).

**Rotation is deliberately NOT shown as euler angles.** Measured: `quat::get_pitch/get_yaw/get_roll` do not invert the `q1*q2*q3` composition that both the UI and the `object_set_transform` MCP tool use — 30 deg about X reads back as 27.7, and `[10,80,10]` as `[63,68,63]`. So a euler box would drift and jump as soon as it round-tripped. The Inspector offers a read-only quaternion, one row of pitch/yaw/roll DELTAS about the object's own axes, and an absolute axis-degrees setter using that same composition. Settling the conventions in `type_quat.h` is its own job; until then, do not add a euler widget.

**Relative moves resolve to ABSOLUTE at the UI boundary.** "Move forward 0.1" would otherwise apply against whatever pose the object has when the physics thread reaches it, and "forward" is the object's own axis, which only the caller knows. Reading the pose in the UI is safe — `physics_mutex` is held.

**Three bugs found and fixed while in there:**
1. **The `[TEST] Ray - Plane Intersection` header teleported the selected object every frame it was open** — an unconditional `selected_object->SetPosition(at)` in the render loop, no button, no drag check. Whole section removed at the user's request. `projection_plane` itself stays: Grid, IsoAnimation and Animation use it, and those two apps have their own copies of the same widget, which were left alone.
2. **`UpdateUICameraControls` seeded znear from the wrong camera** — read `main_scene->camera->viewport.znear`, wrote `camera->viewport.znear`, so inspecting a selected camera object wrote the main camera's znear onto it.
3. **Two 20-line inline blocks of eight collision-mask checkboxes** collapsed into `RenderBitmaskCheckboxes`.

Also removed: the empty `UpdateUIPhysics(Physics*)`, and `RenderSelectedObjectUI` / `UpdateUISceneObjectTree` (no callers outside `Application`).

**Destroy leaks, and it is now MEASURED, not inferred.** My earlier note in `SimCommand.h` that there was "no teardown path" was wrong: `Object::Destroy()` marks a flag and `Renderer::DeleteDestroyedObjects()` does the deleting — but only **Dozer** and **Ship** ever call it. Measured via `sim_command object_destroy`: the object count stayed at 65 with the destroyed duplicate still listed. So in the other eight apps a destroyed object stops rendering while its rigid body stays in the world forever. `SIM_CMD_OBJECT_DESTROY` marks and wakes the world, exactly as the old button did — deliberately NOT adding a new reap call site, because `Renderer::GetAllRenderableVisableSubObjects` walks the object tree from `Scene::DrawFrame`, which runs **outside** `physics_mutex`, so deleting from the physics thread races it. That race already exists in Dozer and Ship. The real fix is to bring that walk under the lock or double-buffer the renderable list, which is a Renderer/threading job, not a panel job.

**Vehicle input model + tank drivetrain (2026-09-06, user-led):**
The user reshaped the vehicle input surface: `Vehicle::ThrottleInput/SteerInput/BrakeInput`, each a scalar (-1..+1, brake clamped 0..1), forwarded from key, stick or scripted player alike. `idle_brake` was **removed** on the grounds that it should be friction with its own parameter. Each drivetrain decides what the inputs mean: `BuggyCharacter::InputToPedals` converts them to gas/brake pedals plus a gear (sign of throttle) and walks `steering_position` TOWARD `steer_input` at `steering_speed` per tick (target-seeking, not incremental - incrementing by `steering_speed*|input|` nets zero against `DecaySteering` and leaves a half-deflected stick stuck). The tank has no pedals: its two tracks take a signed command each.

**Three real bugs found in the tank drivetrain, with evidence:**
1. **Lever mixing was wrong.** It multiplied BOTH sides by the steering magnitude, so steer 0 gave zero drive on both sides and full steer always zeroed one side - only straight-ahead and pivot-in-place were reachable. Correct mixing is `left = throttle + steer`, `right = throttle - steer`, clamped per side. That reproduces the real two-lever control exactly and every intermediate is reachable.
2. **`setBrakeTorque` cannot be used for a small drag.** In rp3d the brake torque DOMINATES the drive torque rather than summing with it, so a per-track rolling-resistance of even 0.09 N applied through the brake channel made the tire transmit ZERO longitudinal force - the track span up to top_speed and the tank would only turn at exactly full lock (where that drag happened to be 0). Route any such drag through the DRIVE channel (a retarding drive force opposing `wheel.angular_velocity`, which is negative while rolling forward), where the two add. This is the same "brake torque wins in rp3d" gotcha already recorded for the tank's idle brake.
3. **`GovernedDriveForce` quantised away the command magnitude.** It clamped to `0.5*mass*headroom/dt` (~50 N/wheel) while the engine asked for 333 N at full lever, so EVERY command above ~0.15 produced the identical force and the lever became a direction switch. Fixed by giving it a `speed_fraction` argument so it governs to `top_speed * fraction`; throttle response is now proportional (measured 0.93 / 0.84 / 0.71 / 0.49 m/s across lever positions where it used to be 0.93 for all of them).

**STILL OPEN - the tank does not yaw on a same-direction track differential.** Full symptom table, everything ruled out by measurement, and the agreed plan to reproduce it in rp3d's own testbed now live in [[tank-yaw-differential-bug]]. Note the speed-proportional governor above also cost the half-magnitude pivot, likely the same underlying threshold.

**Probe gotcha that produced two wrong conclusions before this was sorted out:** a `tank_steer`/`tank_drive` hold lasts `duration_ms` worth of TICKS, so a hold longer than the steps taken stays active into the next test case and contaminates it. Always `tank_drive direction=stop` + `tank_reset` between cases, and size the duration to the steps. Also `vehicle_mcp`'s `App` has no `stop()`, so probe scripts leave `wind.exe` running and the next link fails with "cannot open output file wind.exe: Permission denied" - kill strays before building.

**Scope rule for the command queue (2026-09-10):** a SimCommand is for a mutation arriving from
OUTSIDE the simulation - another thread's (UI, MCP), and for step 7 a tick-stamped note of external
intent. Mutation the sim causes itself must NOT go on the queue: a replay reproduces it by
reproducing the cause, so a recorded command would apply it a second time on top. Ask "who decided this?" - a person or a tool: queue
it; the simulation itself: keep it in-sim and defer it to a safe point in the tick.

ApplicationShip is now the worked example of both halves (2026-09-10). External: `SHIP_CMD_SPAWN_ASTEROID`
(= SIM_CMD_LAST+0), `SHIP_CMD_SPAWN_DOOR` (+1) and `SHIP_CMD_SPAWN_PICKUP` (+2), registered in
`RegisterCommandHandlers`, used by the "Add Asteroid"/"Add Door Panel"/"Add Pickup" buttons via
`SubmitUICommand` and by the `asteroid_spawn`/`pickup_spawn` MCP tools via `SubmitCommandAndWait`.
None could be `SIM_CMD_OBJECT_SPAWN_ASSET`, which deliberately makes no physics body - an Asteroid
carries a sphere collider and the ship's masks, a door is two bodies plus a hinge joint, and a
Pickup's collider is a trigger. The pickup command shows what `subtype` and `value[]` are for: the
PickupKind rides in `subtype` and the amount in `value[0]`, no struct change needed. Internal: the asteroid explosion is spawned from a staging vector
(`pending_asteroid_explosions`) drained at the top of `RunSimulationTick`, NOT via a command - what needed
deferring there was re-entering rp3d from inside `onContact`, not crossing a thread.

One thing that follows from making the command self-describing: a caller that rolls dice must roll
them itself and put the RESULTS in the command (the Add Asteroid button does), or a replay would
re-roll. That does not close the hole that the roll itself consumes from the sim's shared generator
off-tick - see [[rrand-shared-stream-todo]], still open.
